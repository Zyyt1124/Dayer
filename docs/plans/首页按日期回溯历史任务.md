# Dayer 第三期：首页按日期回溯历史任务

> 归档说明：本文是 2026-10-08~09 那一期的实施计划原文，已完成并提交（`2792807`）。
> 从 `.claude/plans/` 归档到这里，是因为 `Index.ets` / `TaskDao.ets` 里多处注释引用「见计划」，
> 而计划文件本身在项目目录之外、不进 git，容易被弄丢。
> 追溯口径的确切后果与刻意取舍另见记忆文件 `dayer-historical-day-view`。

## Context

**要解决的问题（现状都是核对过代码的客观事实）：**

1. 首页数据源写死 `TaskDao.queryToday()`（`Index.ets:89`），SQL 是
   `创建时间 ∈ [今天零点, 明天零点) OR 状态 IN (待开始, 进行中)`（`TaskDao.ets:47-51`）。
   于是**已完成、且不是今天创建的任务，在应用里没有任何入口**。全工程只有 3 个页面
   （`Index` / `TaskDetailPage` / `TaskEditPage`），没有历史页、没有日期切换，唯一的日期选择器
   在编辑页里选截止时间。数据仍在库里（`queryCompletedDurations` 读得到全部已完成行），只是用户看不到。

2. **现存缺陷**：一个 10-05 创建、今天完成的任务，**在点「完成」的那一瞬间就从首页消失** ——
   它掉出了 `create_time` 区间，又不再是「未完成」。用户刚做完一件事，它就不见了。本期口径顺带修掉它。

需求文档 §四.3 明确要求「支持随时回溯过往每日任务、耗时数据、复盘记录」，而「复盘」正是这个应用唯一的差异化。

**本期目标**：首页顶部能左右翻日期，看任意过去一天的完整列表（含预估 vs 实际偏差），点进详情页。

## 已确认的决策（你已选）

1. 归档口径 = **创建于该日 ∪ 结束于该日**（同一任务可能出现在两天）。
2. 入口 = **首页顶部**，不新建独立页面。已核实 `Navigation.title(value: ResourceStr | CustomBuilder | NavigationCommonTitle | NavigationCustomTitle, options?)`
   （`navigation.d.ts:2324`，**@since 8、无 @deprecated**）接受 `CustomBuilder`，所以切换条放进 title 区，
   顺带解决 `.title($r('app.string.home_title'))` 写死「今日」、翻到历史日就说错话的问题。
3. 不往未来翻。

## 口径的确切后果（先写清楚，免得后面当成 bug）

- 10-05 创建、10-07 完成 → **10-05 与 10-07 都能看到**。
- 10-01 创建、10-05 开工、10-08 完成 → 只在 10-01 和 10-08 出现，**10-05 看不到**（那天既非创建日也非结束日）。
- 从没结束的跨天任务 → 只在「今天」的视图里（保留现有「未完成的不能消失」意图）；等它哪天结束了，才出现在那一天。

## 改动清单

### 1. `entry/src/main/ets/common/TimeUtil.ets` — 按日历天取区间的纯函数

现有 `startOfToday(now)`（:120）与 `startOfTomorrow(now)`（:127）实现上对**任意**时间戳通用
（`setHours(0,0,0,0)` / `setDate(getDate()+1)`），只是名字带 Today。新增：

```ts
/** 任意时刻 → 当天本地零点。startOfToday 的泛化，名字不再绑死「今天」 */
export function startOfDay(anchor: number): number

/** 半开区间 [当天零点, 次日零点)。用 class 而非对象字面量，规避 arkts-no-untyped-obj-literals */
export class DayRange { start: number; end: number; constructor(start, end) {...} }

/**
 * 按**日历天**平移，保留本地钟面时刻。
 *
 * ⚠️ 绝不能写成 anchor ± delta * 86400000：一天的毫秒数不是常量。有夏令时/时区规则切换的
 * 地区，某一天只有 23 小时或长达 25 小时，加减固定毫秒会落到相邻那天的 23:00 或 01:00 ——
 * 对一个「日零点」锚点来说就是整体错了一天，半开区间随之整段偏移。setDate 走日历运算，
 * 闰年、月末、跨年由运行时统一处理（1/31 +1 → 2/1，不是「32 日」）。
 * 因此本文件**刻意不提供 MS_PER_DAY** —— 提供了就一定会有人拿它去做日的加减。
 */
export function shiftDays(anchor: number, delta: number): number
export function isSameDay(a: number, b: number): boolean
export function dayRangeOf(anchor: number): DayRange
```

把 `startOfToday` / `startOfTomorrow` 改为委托（`startOfToday → startOfDay`，
`startOfTomorrow → dayRangeOf(now).end`）：行为逐位不变（现有 `TimeUtil.test.ets` 断言的是行为，
不用改一行），同时消除「两处各写一遍日界」的漂移源。`endOfDay`（:134，23:59:59.999）**保持不动** ——
它的语义是「当天最后一刻」，给详情页的 deadline 用，与半开区间是两回事，别混用。

### 2. `entry/src/main/ets/data/TaskDao.ets` — 新增按天查询，复用 `queryTasks`

```ts
/** 某一天的任务：创建于该日 ∪ 结束于该日。includeUnfinished 只对「今天」为真 */
static queryByDay(dayStart: number, dayEnd: number, includeUnfinished: boolean): Promise<Task[]>
```

```sql
SELECT * FROM task
WHERE (create_time >= ? AND create_time < ?)
   OR (actual_end_time >= ? AND actual_end_time < ?)
ORDER BY status ASC, priority DESC, create_time ASC
```

- 绑参 `[dayStart, dayEnd, dayStart, dayEnd]`。
- **`includeUnfinished` 为真时追加 `OR status IN (0, 1)`，且只对「今天」为真。** 这是必须保留的：
  旧 SQL 靠这个分支让「昨天创建、仍未开始」的任务不从首页消失，`QUERY_TODAY_SQL` 的注释也写明了
  「未完成的跨天任务不能从列表里消失，否则用户会以为它被删了」。历史日**绝不能**加这个分支 ——
  那会把所有未完成任务灌进每一个过去的日子。
- `actual_end_time >= ?` 前面**显式写上 `IS NOT NULL`**。严格讲不加也对（SQLite 三值逻辑下
  `NULL >= x` 求值为 NULL 即假），但零代价换来两件事：读的人不必在脑子里过一遍三值逻辑；
  日后若给这列建索引，显式判空让优化器更容易走区间。
- 单表 WHERE 用 OR，一行最多命中一次，OR 不产生重复行，**不需要 DISTINCT**（已核实无 JOIN）。
- **常量声明顺序有硬约束**：`TaskDao.ets:15-20` 的注释写明 SQL 模板串在模块加载时求值，
  引用**后**声明的 const 会撞 TDZ。`QUERY_BY_DAY_SQL` 必须放在它引用的所有常量（`TABLE_TASK`、
  `TaskCol.*`）**之后** —— 跟着 `QUERY_BY_ID_SQL`（:53）后面放是安全的。
- 内部走现有的私有 `queryTasks(sql, args)`（:221），复用 13 列读取与 NULL→0 哨兵映射（:252-257）。
- **替换掉 `queryToday()` 与 `QUERY_TODAY_SQL`**：「今天」就是同一条查询加 `includeUnfinished=true`，
  一条 SQL 比两条好。已 grep 确认 `queryToday` 只被 `Index.ets:89` 调用，没有别的引用点。
- **不动 `DB_VERSION` / `MIGRATIONS`**：版本号只驱动 DDL，本次只加 SELECT。已核实 `Migration.test.ets:25`
  断言 `migrationSteps(DB_VERSION, DB_VERSION).length === 0` —— 多此一举地升版本反而是唯一会弄红它的做法。
- **不加索引**：`task` 表目前无任何索引；单机个人数据量下不值得为此写迁移。

### 3. `entry/src/main/ets/pages/Index.ets` — 日期状态、切换条、按 `isToday()` 分支

新增字段：`@State selectedDayStart: number = 0;` —— 所浏览那天的**本地零点**，不是任意锚点。
每次移动都用 `startOfDay(...)` 归零后再赋值，让状态本身是规范形式（比较和展示都直接可用）。
**时序是关键**：在 `aboutToAppear` 里必须在 `this.tick = Date.now();` **之后**、`this.reload();` **之前**
写 `this.selectedDayStart = startOfDay(this.tick);` —— 否则首次 `reload` 会拿 0 去查 1970-01-01。

| 位置 | 改动 |
|---|---|
| `isToday()` | `return isSameDay(this.selectedDayStart, this.tick);` —— ⚠️ 读 **`this.tick`**，不写 `Date.now()`（全页唯一时间源，见 `:39-46` 既有注释） |
| `goPrevDay()` / `goNextDay()` / `goToday()` | `this.selectedDayStart = startOfDay(shiftDays(this.selectedDayStart, ∓1));` 后调 `reload()`；`goNextDay()` 在 `isToday()` 时直接 return，且「后一天」按 `canGoNextDay()` 置灰。`goToday()` 用 `startOfDay(this.tick)`。事件回调里读 `Date.now()` 是允许的 —— 约束只针对 `build()` 与 `@Builder` |
| `reload()` | `const range: DayRange = dayRangeOf(this.selectedDayStart);` → `TaskDao.queryByDay(range.start, range.end, this.isToday())`。**`loadToken` 竞态令牌那套原样保留** —— 连点两下箭头会并发两次查询，这套机制正是为它准备的。catch 里的日志文案 `queryToday failed` 改成 `queryByDay failed` |
| 切日时是否清空 `tasks` | **不清**：本地库查询近乎瞬时，保留旧内容直到新结果到达，比「先清空再填」少一次闪。真机上若仍觉错位，再补 `this.loaded = false` |
| `syncTicker()` | 条件加上 `isToday()`：`visible && isToday() && hasRunningTask()`。历史日不该有 30 秒一跳的表在跑（也符合 `Claude.md` §五） |
| `build()` 第一行 | `if (this.isToday() && this.focusTask() !== null) { this.RunningCard() }`。「进行中卡片」是「此刻」的 affordance，历史日出现就是错的：历史日结果里完全可能含 `IN_PROGRESS` 行（那天创建、至今没做完） |
| `EmptyState()` | 文案按 `isToday()` 分支，历史日用新键 `history_empty`「这一天没有任务」；历史日**不显示** `home_empty_hint`（「新建一个任务…」在历史日没有意义） |
| 底部新建按钮 | `if (this.isToday())` 才渲染。历史日点新建，`createTime` 是此刻，新任务不会出现在正在浏览的那一天 —— 按钮做一件事却在别处生效，比隐藏更糟 |
| 新增 `@Builder DaySwitcher()` | 用 `.title(this.DaySwitcher)` 挂上：`‹ 日期 ›`，非今天时箭头下方多一个「回到今天」。日期文案：今天 → 复用 `home_title`「今日」、否则 `formatDate(this.selectedDayStart)`（复用 `TimeUtil.ets:145`，输出 `2026-10-05`）。**无参 @Builder**，内部读 `this.selectedDayStart` / `this.isToday()` / `this.canGoNextDay()`。`@Builder` 内间距只用 `.margin()`/`.padding()` —— Row/Column 的 `space` 收不了 `$r()` |

### 5. 单测（扩写 `entry/src/test/TimeUtil.test.ets`）

- `shiftDays` 跨月：3月1日 −1 天 → 2月28日（平年）/ 2月29日（闰年 2024）。
- 跨年：1月1日 −1 → 上年 12月31日；12月31日 +1 → 次年 1月1日。
- **相邻日无缝拼接**（本组最有价值的一条）：`dayRangeOf(x).end === dayRangeOf(shiftDays(x, 1)).start`
  且 `dayRangeOf(shiftDays(x, -1)).end === dayRangeOf(x).start` —— 保证没有任何时间戳落在两天区间的缝里、
  也没有重叠，这正是「某个任务哪天都查不到」这类 bug 的防线。
- `isSameDay`：同一天不同时刻为真；跨零点相差 1 毫秒为假；`dayRangeOf` 的右端点（次日零点）不属于前一天。
- `startOfToday` / `startOfTomorrow` 委托后行为不变（原有用例即回归网）。

**诚实说明覆盖不到的地方**：`isToday()` 门控 RunningCard / ticker / 空态文案 / 新建按钮这几条是 UI 分支，
`TaskDao` 因为 import `@kit.ArkData` 进不了本地单测（这是本工程「不 import `@kit` 才测得了」的既有边界，
`TimeUtil.ets:5-6`、`Migration.ets:6-9` 都把这条写成前提）。这几条**只能靠真机验收**，不在单测里假装覆盖。

## 风险：最可能翻车的地方，以及怎么先探掉

1. **`Navigation.title(CustomBuilder)` 是否随 `@State` 刷新** —— SDK 只保证签名可用（@since 8），
   不保证刷新时机。这是本期唯一的结构性未知，**所以前三步都刻意避开 title 区，把它放到第 4 步单独探**
   （见实施顺序）。
   `.title(this.DaySwitcher)` 传的是**函数引用**，`selectedDayStart` 变化时 `Index.build()` 会重跑，
   但 ArkUI 对「属性值是同一个函数引用」是否触发标题区重建属于框架实现细节。若不刷新，症状是：
   点了「前一天」，列表变了、日期标签还停在「今日」—— 与 `TaskDetailPage` 那个「@Builder 停在首帧」
   是同一族 bug，**编译器不报错、单测也测不出**。
   **兜底方案**：把 `DaySwitcher` 从 `.title()` 挪回 `Column` 作为第一个子节点（`Index.ets:475`
   现在的第一个子节点是条件渲染的 RunningCard，前面插一个自绘日期栏不影响布局），`.title()` 改回静态。
   Column 内的 `@Builder` **必然**随 `@State` 刷新，是确定能工作的路径，且同样能修掉「今日」写死的问题。
2. **`this.tick` 的依赖是否在 title 区被注册** —— 与风险 1 同源：若标题区是独立渲染上下文，
   `isToday()` 读的 `this.tick` 可能不被登记进 `Index` 的依赖表，那 `onPageShow` 里 `tick = Date.now()`
   就不会让日期栏重算。兜底方案同样解决。
3. **`@Builder` 必须无参**：`DaySwitcher()` / `EmptyState()` 都不许带参数，内部读 `this.*`。
   带参（尤其两个及以上）会按值传递、状态变了不刷新 —— 本项目已经为此吃过一次：
   `TaskDetailPage` 的 `MetricColumn(label, value, color)` 整块对照卡片永久停在首帧，
   编译器不报错、单测也测不出。在 Column 内渲染时，`isToday()` 读的 `this.tick` 会被正常登记成依赖，
   切换条与卡片随 tick 重建正是想要的。
4. **`$r()` 放进三元表达式、`.enabled()` 挂在 Text 上** —— 都属于不常见但应合法的写法
   （`enabled` 是 `CommonMethod`，@since 8），真机核验标题栏时一并看。
5. **已知限制（接受，写进代码注释）**：跨零点时若正停在「今天」，`tick` 前进会让 `isToday()` 翻成假 ——
   卡片消失、空态文案变，但列表不会重查。ticker 只在有进行中任务时才走，所以只在那种情况下发生；
   若当天无进行中任务、用户又停在前台跨零点，则 `tick` 根本不前进，日期栏与数据一起停在昨天。
   **可选改进**（本期不做）：用 `0` 当「跟随今天」的哨兵，翻页时才落定具体日期。
6. **无索引**：`task` 表无任何索引，历史日查询走全表扫。日常量下可忽略；动索引要改
   `DB_VERSION`/`MIGRATIONS`，超出本期范围，记为已知取舍。

## 实施顺序（每步都能独立验证，风险从低到高）

1. **纯函数层**：`TimeUtil` 加 `startOfDay` / `DayRange` / `shiftDays` / `isSameDay` / `dayRangeOf`，
   让 `startOfToday` / `startOfTomorrow` 委托；扩写 `TimeUtil.test.ets`。
   验证：本地单测全绿，且**现有 TimeUtil 用例一行不改仍全绿**（这是委托改造的回归网）。
2. **数据层**：`TaskDao` 加 `QUERY_BY_DAY_SQL`（放在 `QUERY_BY_ID_SQL` 之后）+ `queryByDay`，删 `queryToday`。
   验证：编译通过 + grep 无超版本警告。DAO 进不了本地单测（import `@kit.ArkData`），靠第 5 步真机。
3. **接上当日区间 + `isToday()` 门控**（先不碰 title 区）：`Index` 加 `selectedDayStart`（`aboutToAppear`
   里 tick 之后、reload 之前初始化）、`isToday`、`reload` 改调 `queryByDay`，并加上 RunningCard /
   ticker / EmptyState / 新建按钮四处的 `isToday()` 分支。
   验证：启动首页与改动前**完全一致**（今天的数据、进行中卡片照旧）—— 此时回归面最小。
   然后用**临时手段**把 `selectedDayStart` 设成昨天，真机确认历史日四处的分支都对（无卡片、ticker 停、
   空态不说「今天」、无新建按钮），空态文案先借用 `home_empty` 两键。验完撤掉临时改动。
4. **探针 + 日期切换条**（本期唯一结构性未知，放在最后做）：加无参 `@Builder DaySwitcher` 与

   **不刷新就立刻切兜底**（把 `DaySwitcher` 挪进 `Column` 顶部，`.title()` 改回静态），这是确定能工作的路径。
