# Dayer 第四期：历史日补记

## Context

上一期做了「首页按日期回溯历史任务」（`‹ 日期 ›` 翻到过去任意一天，看那天的完整列表）。当时**刻意砍掉了补记能力**：新建任务的 `create_time` 写死 `Date.now()`（`TaskEditPage.ets:194`，全工程唯一写入点），所以在历史日新建出来的任务会落到今天 —— 一个按钮做完事却在别处生效，比不显示更让人困惑，于是历史日干脆不渲染那个按钮。

结果是回溯功能只读：翻到 10-05 发现漏记了一件事，只能干看着。本期把这块补上。

需求文档 §四.3 要求「支持随时回溯过往每日任务」，补记是让这条闭环真正可用的最后一环。

**已知且接受的后果**：补记出来的任务是「待开始」，所以按现有规则（`QUERY_TODAY_SQL` 额外 `OR status IN (0,1)`：未完成的跨天任务不能从今天的列表消失）它**会同时出现在今天的列表里**。这是既有规则的自然延伸，不是 bug，要在代码注释里写明。之后要记实际耗时，走详情页既有的「记录实际用时」。

## 已确认的决策（你已选）

1. 补记出来的就是**普通「待开始」任务**，编辑页不加「实际用时」输入框，不直接建成已完成。改动最小。
2. 归属日 = 首页正在浏览那一天的**本地零点**（`selectedDayStart`）。它必然落在 `dayRangeOf` 算出的 `[那天, 次日)` 半开区间内，所以 `queryByDay` 的「创建于该日」分支一定命中。因为是 00:00，在 `ORDER BY status ASC, priority DESC, create_time ASC` 里同状态同优先级排最前。

## 参数传递：给 `TaskRouteParam` 加字段（而不是新建 class）

`RouteName.ets` 的 `TaskRouteParam` 加 `createTime: number`（**0 = 用此刻**，沿用 `Task.ets` 「0 表示未设置」的既有哨兵约定）：

```ts
export class TaskRouteParam {
  taskId: number;
  /**
   * 新任务的创建时间戳；**0 = 用此刻**。
   * 只有「首页翻到历史日后补记」这条路会填它，填的是那一天的本地零点。
   * 详情页路由复用同一个类，但它永远不读这个字段。
   */
  createTime: number;

  constructor(taskId: number, createTime: number = 0) {
    this.taskId = taskId;
    this.createTime = createTime;
  }
}
```

为什么不新建独立 class：详情页与编辑页共用这一个类，拆开要么引入联合类型（本工程零先例，`.navDestination()` 的 builder 签名是否收联合类型**没核对过**），要么用继承 —— 而继承也跑不掉 0 哨兵（`TaskDetailPage.ets:305` 进编辑传的是基类实例），结果是多一层继承、多一次 `instanceof`，哨兵一个没省，还要改两个跟补记无关的调用点。

**默认参数的风险与退路**：本工程 9 个 constructor **零个**用过默认参数，没有先例。查过本机 SDK 里 ArkTS linter 的 105 条 `arkts-*` 规则，**没有任何一条涉及默认参数或可选参数**（参数相关的只有 `arkts-no-destruct-params` / `arkts-no-ctor-prop-decls`），所以预期能过。**第一次编译要单独盯 `RouteName.ets`**；若被拒，退路是把第二个参数改成必填，给 3 个既有调用点（`Index.ets:369`、`Index.ets:374`、`TaskDetailPage.ets:305`）各补一个 `0`，机械 3 行。

## 验收（模拟器 `127.0.0.1:5555`）

**SQL 三条铁律**（上次踩过 `unixepoch` 被 shell 吃掉的坑）：① 整条 SQL 不出现单引号、不出现括号；② 不用 `datetime()`/`unixepoch`/`strftime()` 这类要写格式字面量的函数，一律取回原始毫秒数在主机上比对；③ 时间戳在主机算好，直接贴十进制数字。

数据库 `/data/app/el2/100/database/com.example.dayer/entry/rdb/dayer.db`，表 `task`。

### A. 老路径回归（最先验）

1. 停在今天，确认按钮文案仍是「**新建任务**」。
2. 记下主机时刻 `date +%s`，点新建、填标题预估、保存。
3. `select id,status,create_time,estimated_minutes from task order by id desc limit 5`
   断言：`create_time` 在点击前时刻 ±60000 ms 内，**不等于任何零点整**；`status = 0`。
4. 任务出现在今天列表；进详情页「创建日期」= 今天。
5. 从详情页进编辑、改标题保存 → 再查同一条：`create_time` **一字不变**。

### B. 新功能

1. 点 `‹` 翻到 3 天前 → 日期条变成 `YYYY-MM-DD`，按钮变成「**补记任务**」。
2. 点它 → 编辑页打开，标题是「**补记任务**」，**没有「实际用时」输入框**。
3. 填标题/预估、保存 → 自动返回首页，**且首页仍停在那一天**（不是跳回今天）。
4. 任务出现在正在浏览的那一天的列表里。
5. 落库断言：主机算 `echo $(( $(date -d '2026-10-05 00:00:00' +%s) * 1000 ))`（换成实际那天），比对 `select id,status,create_time from task order by id desc limit 3`。
   **断言 `create_time` 精确等于**那个毫秒数 —— 半开区间差 1 ms 就换天，不允许「差不多是那天」。同时 `status = 0`。
6. **确认「已知后果」真的发生了**：点「回到今天」→ 这条任务**必须出现在今天列表里**，且排在最前（它是 00:00）。要确认它在，不是漏了。
7. 点进这条任务：详情页「创建日期」显示**那一天**，状态「待开始」。
8. 同一天连续补记两条 → 两条都在。
